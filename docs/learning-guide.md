# 从理解到亲手完成这个项目

这是一项有监督文本分类任务：训练数据告诉我们“这段文字由哪个模型生成”，程序从中学习模式，再给没见过的文字预测来源。当前用的是传统机器学习基线；我们没有训练或调用18个大模型。训练好的分类器本身也不是一个聊天机器人。

## 一段文字怎样成为预测

以下只用自造短句解释，未复制比赛文本。

```text
输入：“A tiny synthetic example.”
    ↓
词/字符片段统计，例如 tiny、example、tin、iny
    ↓
TF-IDF：将片段转成数字特征
    ↓
逻辑回归：为18个候选类别计算分数并得到概率
    ↓
输出：一个候选模型名称
```

TF-IDF会考虑片段在当前文本中的频率和在训练语料中的普遍程度。它是统计表示，并不等于理解语义。这里同时统计词片段与字符片段，可能捕捉词汇、标点和拼写习惯；某个特征是否真的有用，需要实验确认。

模型训练就是用带标签的文字调整分类器参数。验证则是在训练时暂时留出一部分已知标签的数据，模拟新数据，测量预测表现。最终全量训练完成后，才预测真正没有标签的test。

## 为什么不能随意随机切分

同一个prompt是同一道问题，不同模型会各写一份回答。如果这道问题的部分回答在训练、另一部分在验证，验证就不能很好模拟“新问题”。所以这里按prompt_id分组，把同一道问题的回答放在同一折。

5折验证会做5次训练，每次留出一组问题，保证每条训练记录都有一次“未参与训练时的预测”。这些拼起来叫OOF（out-of-fold）预测。TF-IDF的词表也必须只在每折训练部分拟合，否则验证数据已经影响了模型输入表示。

Balanced accuracy先分别算18个类别各自的召回率，再平均。例如某一类真实有10条、认对3条，它的召回率就是30%。这与“所有样本一起算认对比例”不同。当前5折平均约29.97%，不能把它理解成每一类都认对29.97%。

## 代码分成哪几类

| 分类 | 文件 | 作用 | 第一遍是否要读 |
| --- | --- | --- | --- |
| 数据入口 | [data.py](../src/ntl_baseline/data.py) | 读取CSV、检查列/标签/id、校验提交、导入ZIP | 先看validate_train和load_competition_data |
| 模型与验证 | [baseline.py](../src/ntl_baseline/baseline.py) | build_pipeline组装模型，make_folds分组，cross_validate产出OOF和指标 | **最先读** |
| 配置与类别 | [config.py](../src/ntl_baseline/config.py)、[constants.py](../src/ntl_baseline/constants.py) | 参数与18个精确类别名称 | 配合baseline阅读 |
| 流程组织 | [workflow.py](../src/ntl_baseline/workflow.py) | 串联审计、验证、训练、保存、预测 | 理解模型后读 |
| 命令入口 | [cli.py](../src/ntl_baseline/cli.py)、__main__.py | 将终端命令转成函数调用 | 会跑命令后读 |
| 可追溯性 | [artifacts.py](../src/ntl_baseline/artifacts.py) | 保存JSON/Parquet、环境信息与哈希，拒绝覆盖 | 第二遍读 |
| Kaggle交付 | [notebook.py](../src/ntl_baseline/notebook.py)、notebooks/official_baseline.ipynb | 从同一套源码生成可独立运行Notebook | 最后读；生成文件不适合从头学代码 |
| 质量保障 | tests/、scripts/check_repository.py | 防止数据泄漏、格式错误、误覆盖和敏感文件混入 | 每读一个模块就看对应测试 |
| 辅助脚本 | scripts/ | 离线执行、生成Notebook和独立官方代码对照 | 按需读，不是另一套主模型 |

核心阅读顺序是 **config/constants → baseline.build_pipeline → baseline.make_folds → baseline.cross_validate → workflow**，不需要先读完所有工程辅助代码。

## 由你完成的学习路线

每一步先由你操作和写结论，我再审查；下表不是已完成的个人能力证明，也没有预先代填答案。

| 步骤 | 你来做 | 验收方式 |
| --- | --- | --- |
| 1 讲清任务 | 用自己的话写输入、输出、训练标签和prompt_id各是什么 | 能解释为什么不是“检测人类还是AI” |
| 2 读懂数据 | 自己运行audit，解释条数、类别数与prompt分组统计 | 不依赖复制原始段落展示理解 |
| 3 读懂模型 | 在build_pipeline中找出两种特征和分类器；解释fit与predict | 能说清哪个步骤在学习词表 |
| 4 理解验证 | 阅读make_folds及对应测试，解释同一prompt跨折的风险 | 画出训练/验证的分组关系，解释OOF |
| 5 独立复现 | 自己选择新输出目录，运行验证、训练和预测 | 解读自己的metrics、确认原件未变 |
| 6 提出实验 | 先写假设、对照、固定指标和资源预算，再讨论一个小改动 | 先审查设计，再由你实现；不提前代做 |
| 7 写作品集 | 整理问题、方法、验证、结果、局限和你自己的贡献 | 能现场解释一个模块与一次失败实验 |

现在从第1步开始：请先尝试写3句话——输入是什么、输出是什么、prompt_id为什么影响验证。此处没有填好的标准回答；我们下一轮围绕你的理解继续，不抢先做第6步。

## 怎样诚实地成为自己的作品集

当前方法来自官方基线，工程框架由AI辅助搭建，当前指标是本机运行记录；这不等于你已经独立完成建模。你可以在理解并亲自复现后，把它作为“AI辅助的机器学习复现项目”，清楚标注来源与协作方式。

之后由你亲自完成的数据分析、测试、实验假设、实现、失败分析和结果解释，才逐项写成你的具体贡献。保留日期、提交与实验记录，不补写不存在的实验，不把暂未完成的计划当成果。作品集的价值在于你能解释并维护它，不只是展示一个分数。
